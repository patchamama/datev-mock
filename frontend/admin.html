Backend target & DATEV connection settings
NTLM is UI-only. A real NTLM authentication handshake cannot be completed from browser JavaScript with an arbitrary username/password — there is no fetch()/ XMLHttpRequest API for it (browsers only do NTLM transparently via Integrated Windows Authentication, using the OS's own logged-in identity). This option exists for future/manual use only; selecting it does not attempt any NTLM handshake, and no NTLM header is added to requests. Check "Route through local relay" below to actually send NTLM credentials to the target — the relay makes the real handshake server-side, where it's a solved problem.
Security note: the relay endpoint accepts an arbitrary target URL/method/headers and makes that real outbound call from wherever this project's backend runs — an SSRF-shaped capability by design. Accepted here because this is a local developer tool run against your own machine/network, not a hosted multi-tenant service.
This page's own JavaScript always makes every API call (settings, master-data/accounting, overrides, stored records, the live request log, and everything in the catalog below) against the base URL composed from Protocol + Hostname + Port + URL path prefix above, instead of assuming it's hosted next to its backend. Leave Hostname/IP empty to use this page's own origin (today's default behavior, e.g. this FastAPI mock) — every other field is then ignored for URL composition. Point it at another local instance (e.g. hostname 127.0.0.1, port 58452 for the FastAPI mock, or port 58553 for the Spring Boot mock), the real DATEV API, a DATEV test endpoint, or any other DATEV-compatible mock — no code changes needed, only that target's own auth/TLS/CORS posture applies (a real DATEV instance must itself send CORS headers allowing this page's origin, or the browser will block the response no matter how these settings are configured). Basic auth is sent as a real Authorization: Basic ... header on every request this page makes, except the live request-log stream below: browsers' EventSource API cannot set custom headers at all (a browser-platform limitation, not a bug here), so that one connection only works unauthenticated or same-origin regardless of this setting. Connect/read timeouts are an honest approximation, not a precise low-level TCP-connect timeout — see the code comment above fetchWithTimeouts() for exactly what they can and can't measure from browser JS. Stored per-browser (not synced to the server); saving reloads the page so every card re-fetches from the new target.
